# Evaluation evidence contracts

- Keep expected routing, workflow scenarios, adversarial cases, and observed results distinct. A written expected answer is not a completed evaluation.
- Trigger changes need relevant positive, negative, and overlap cases; preserve specialist ownership, approval, and stop boundaries in the expected behavior.
- Do not delete hard cases or change expected outcomes solely to match the implementation under test.
- Attribute observations to the actual candidate, environment, and invocation. Static validators and smoke fixtures do not certify live model routing or every platform.
- Keep time-sensitive claims tied to inspected primary sources and an honest review date; do not refresh dates without rechecking the claim.

Use [README.md](README.md) for the evaluation format and existing scenarios. Record real limitations rather than filling missing runtime evidence with a plausible narrative.
